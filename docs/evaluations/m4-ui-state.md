# M4 视图高亮与提示栏准入、复用

2026-10-25。搜索/链接装饰数组与搜索、通知、Shell 状态、URL 提示栏的输出文本已接 `ui-reserved`。每个视图持有可复用容量及票据，切换窗格一起交换；绘制提示栏不再克隆 String。搜索状态、通知和 Shell 摘要改为直接格式化到有界输出缓冲，保留原文字和光标裁剪规则。没有新增包、线程、运行时子进程或 UI 定时器。**本页只覆盖这些视图输出数据，不表示 Search 内核/查询、通知/命令存储、侧栏/配置/任务等全部 UI 数据均已计费。**

## 额度、生命周期与失败

装饰最多 `MATCH_LIMIT + 2 = 1026` 项，包含 1024 个搜索范围、当前匹配及悬停链接；扩容前同时预留旧、新容量，完成后按实际容量收费。超过数量上限或准入失败会清除当次不完整装饰，避免把部分前缀当完整结果。搜索引擎中的原匹配和选择没有因此删除。

提示栏 UTF-8 输出最多 64 KiB。格式化时单遍流式写入；每段写入前检查累计长度，必要时先为旧、新容量重叠申请额度再扩大缓冲，失败清空输出。不能把长度检查放在 `format!` 后。搜索前缀、横向滚动、宽字符、组合符号、预编辑下划线和失焦光标隐藏保留原逻辑，提示文本不写入终端网格。

拒绝和超限时用不要求堆分配的静态提示“界面资源额度或长度超限，部分提示/高亮不可用”，不保留旧高亮或旧提示冒充当前内容。下一次正常更新重新尝试；关闭提示栏清空内容但保留已计费容量，供后续复用。视图销毁才归还；渲染缓存回收会释放当前视图的 UI 缓冲并失效旧帧，其他视图仍为自己保留的容量付费。应用后续 `update_ui` 按当前业务状态重建。

绘制时 String 数据短暂移出，票据始终留在 UI 拥有者里；用借用文本及复制的光标元数据绘制，然后放回原缓冲，不申请另一个 String。`Renderer` 与 `ViewState` 交换完整 UI 拥有者，和已经计费的行指纹同样按视图保留，不复制。

## 分配、像素和失败回归

[当前工具链](m4-ui-state-allocation.json)及 [Rust 1.88](m4-ui-state-allocation-msrv.json)均使用临时副本全线程 epoch Rust 请求计量器，保守计算 realloc 的旧、新请求重叠：

- 冷状态装入 1026 个装饰及 64 KiB UTF-8 文本，再交换两个视图、在根额度占满后拒绝新数据、释放全部拥有者。存活/峰值请求与账本均为 **106,576 B**，2 次分配请求、0 次扩容，拒绝没有新增分配，最后归零。本机 Decoration 为 40 B，此数字不是跨平台类型大小承诺。
- 预热真实本机 Congminal/PTY、终端、搜索的 **1024 个匹配**、通知、悬停链接、字体/缓存与画布后，执行 **5000 次 `update_ui` + 500 次更新并强制完整软件绘制**。循环搜索（含中文/组合符预编辑）、通知、Shell、链接和空栏五种模式；两工具链的新增分配、扩容、存活请求和峰值均为 **0**。
- 这项计量不包括预算上下文、原输入/业务状态、PTY/线程启动及预热。它证明这组实际更新/绘制路径的复用，不能推广成整个应用每帧零分配，也不包括用户输入编辑/搜索扫描/通知新增的分配。
- 最初夹具在 App 析构后立即要求整个根额度为零，遇到仍由 PTY 异步关闭持有的 1,146,880 B；当时更新/绘制已是零新增，见[保留的失败](m4-ui-state-allocation-before-pty-wait.json)。最终夹具按最多 5 秒等待原异步关闭归还，再验证总额度和映射数归零；等待在 UI 计量/耗时区间之外，不把它解释成 UI 关闭硬期限保证。

新增四项常规回归覆盖最大/超限数据、UTF-8 和短额度扩容、宽字符/组合符预编辑及 1/5/6/10/19/20/80 列布局、拒绝后的像素、视图交换和缓存回收。既有增量/全绘制像素逐项比较继续通过。[完整回归](m4-ui-state-build.json)：普通 **550** 项、预览主程序 **553** 项及 helper **18** 项通过，专用忽略分别 38/39 项；Rust 1.88 的 `ui` 过滤 **22** 项通过（另 1 个专用忽略），三目标静态 Clippy、格式和默认 release 通过。Windows/Linux 交叉检查仍不算运行验收。

新增分类后本机 Budget/Stats 为 **288/240 B**。[SFTP 文件额度复验](m4-ui-state-file-quota.json)仍为原 16 MiB 子池、9 MiB I/O 余量，最大字段请求 2 个运行/11 个等待后由额度拒绝，最后归零。[Workspace/SFTP 复验](m4-ui-state-workspace.json)请求峰值 **1,957,981 B**，最后计量请求及 SFTP 子/父预留归零；路径、目录选择、审阅、重试和退出的预热直接绘制仍零新增分配。不能推广为原生 SFTP 用户流程已验收。

## 同负载性能

[五组对照](m4-ui-state-cost.json)使用生产 System 分配器，将完全相同的夹具注入[改动前冻结源码](baselines/m4-ui-state-before.tar.gz)与当前临时副本。每版有两次整次预热，再五组交替。每次先预热真实 PTY/app 和 50 个混合完整帧，再计时 5000 次 UI 更新及 500 次更新+强制完整软件绘制，含 1024 搜索匹配及上述五种提示模式。

| 场景 | 五组配对耗时中位变化 | 配对范围 |
|---|---:|---:|
| UI更新 | -67.52% | -67.63% ～ -66.40% |
| UI更新 + 强制完整软件绘制 | +0.39% | -5.46% ～ +1.50% |

UI更新每次的批次折算中位约从1.83µs降到0.59µs；更新+完整软件绘制整体接近。整进程RSS高水位配对中位+96KiB（-32～+144），CPU差值中位-0.01s（-0.01～+0.00）。复用容量与新增票据有保留成本，不宣称零内存代价。逐次样本及P95/P99均在原始报告中，不能将这里的每次折算均值当成输入延迟分布。

所有完整帧的像素哈希累积指纹在改动前后、两工具链计量夹具中相同；每次软件绘制之后才计算指纹，不将遍历画布的验证耗时算入 draw API 区间。原有像素数组逐项回归和拒绝后的像素比较为补充证据。哈希/样本覆盖本机字库及固定场景，不能保证全部字体/交互状态都相同。

计时包含 Instant 与模式切换影响；UI 更新仍需遍历匹配和有界格式化，零分配不等于零 CPU。`time -lp` 的 CPU/RSS 是整个测试进程高水位/总时间，包含 PTY/app 启动、预热、计量外哈希验证、映射/缓存、析构和关闭等待，CPU 分辨率 0.01 秒。不是原生输入、IME/剪贴板、窗口呈现/关闭硬延迟、其他平台或 30 分钟验收；没有新增运行时子进程/线程，原 PTY 子进程和 I/O 线程保持原路径。

[证据核对](m4-ui-state-audit.json)关联六份当前报告、注入夹具、源码/清单、归档与上一字体映射阶段，核对完整样本数量、相同像素指纹、资源释放及原 SFTP 余量。Windows 测试包装接口修正前的报告保留为 `*-before-windows-test-gate.json`。首版复用仍有逐项装饰检查和双遍格式化，单独UI更新耗时比基线慢约30%；原五组报告保留为 `*-before-single-pass.json`，对应源文件也已保留。随后改为已知精确长度的一次装饰准入和单遍文本写入，仍观察到更新约+10.6%、更新+重绘约+3.0%；该批保留为 `*-before-decoration-batch.json`。最终把普通匹配的批量写入与至多两个特殊装饰分开，去掉热循环多层chain，再重新测量；历史报告不代替最终结果。

# M4：固定布局快照与保存元数据

2026-10-26，macOS arm64。布局快照、比较、格式转换及恢复尺寸预检改为固定容量数据；保存任务的共享对象和路径工作区先准入，再创建工作器和执行 IO。没有新增包、工作器、子进程或生产额度，没有改变布局文件的 v1 格式或 8 窗格上限。完整 M4–M8、兼容和三平台/长测仍执行中。

## 实现

- 快照使用最多 15 个节点和 8 个标签的内联数组。持久化编号本就限制为 1–8，现使用 u8；当前两工具链的 Layout 为 128 B。添加失败只回滚本次写入的节点，不复制整份快照。比较只检查有效节点和标签。
- 解析、克隆和尺寸预检不再创建 Vec/Box；序列化使用 4104 B 的固定缓冲对象，最多 4096 字节内容。恢复预检直接遍历快照，沿用原节点布局算法，并用全部焦点、窄窗口和正常窗口验证几何一致。真正提交到 UI 时仍转换为现有 Node，相关通用 UI 容器/节点准入尚待完成。
- Store 的 Shared/Arc、首次 Mutex/Condvar 元数据在分配前计费；最后引用先释放 Arc 控制块，再销毁共享内容和票据。实际两工具链保留请求和额度均为 520 B，最后引用释放后均归零。
- IO 路径拥有者保留输入 PathBuf 容量、一个预先分配的临时路径缓冲及系统路径转换/rename 的保守余量。逐段创建目录，复用路径缓冲；文件内容、临时文件名和错误对象不再依赖动态格式化。错误保留静态消息及 ErrorKind，UI 可显示具体错误类别。调用者在进入 Store 之前构造配置路径的过程仍属于配置/平台元数据待办。
- 保存序号与临时文件序号均检查耗尽，不回绕。保存序号耗尽后拒绝新快照、保留已接收任务并关闭接收；完成/退出仍报告失败。提交拒绝进入可见通知。固定快照更新不析构用户对象，也不在状态锁内执行文件 IO。
- 读取布局时使用打开后的文件属性再次核对普通文件及大小；Unix 使用 NOFOLLOW/NONBLOCK，Windows 静态适配 OPEN_REPARSE_POINT。目录/链接/FIFO 替换不被当作正常布局内容。这里不宣称网络盘 IO 可中断；250 ms 仍只是退出等待的软检查预算。

## 分配和失败边界

[稳定工具链](m4-layout-resources-allocation.json)和 [Rust 1.88](m4-layout-resources-allocation-msrv.json)各运行四个独立进程用例，临时副本使用全线程 epoch Rust 请求计量，生产分配器未改动：

1. 最大 8 窗格树的解析/编码/克隆/几何检查及错误输入各循环 10000 次，新增分配、扩容、live 和 peak 均为零。
2. 实际 8 个本地 PTY 窗格预热至 READY 后，快照和恢复预检循环 10000 次，四项计数同样为零；丢弃后原预算及工作槽归零。
3. 创建实际 Store、新工作线程和同步对象，保存 1000 个合并快照，执行嵌套目录创建、文件 sync/rename，确认最后宽度；保留 Shared 引用到原生线程退出之后，其请求/费用均为 520 B。最后引用释放后请求、预算及工作槽归零。元数据拒绝没有启动工作器，但 prepare 的临时堆票据仍有 1 次分配，不宣称全部拒绝零分配。
4. 实际原生路径失败后等待工作器回收，确认 marker 文件保留、临时文件已删除、预算/请求/工作槽归零。

堆费用比较已扣除 2 MiB 请求线程栈。稳定/MSRV 的保存流程请求峰值分别为 7252/7380 B，扣栈后的账本峰值为 126248 B；包含启动、元数据及拒绝准备的保守费用，并非实际内核栈、C/分配器/OS 或 RSS。

本机 `getconf PATH_MAX /tmp` 为 1024，`NAME_MAX` 为 255。成功用例保存 909 字节路径，并验证应用上限之外的 4097 字节路径在 IO 前被拒绝；名称 300 字节的原生失败用例验证清理。应用的 4096 字节限制不代表文件系统必须支持同长路径；较早误设 3 KiB 成功路径的失败记录保留为 [原生路径边界](m4-layout-resources-allocation-before-native-path-limit.json)。未用缩小成功用例掩盖错误路径的资源回收检查。

首次性能夹具只等待 used=0，随即检查 managed_workers=0，遇到了回收器归还费用和归还工作槽之间的短暂状态；现在等待两个值都归零。这是夹具观察条件的修正，没有把两个状态改为等价，也没有放宽最终值。旧夹具快照保留为 `m4-layout-resources-cost-before-wait-tuple.json`。

## 同负载成本

[原始性能数据](m4-layout-resources-cost.json)：冻结源码/当前源码使用同一个 System 分配器夹具，各两个预热后五组交替配对。真实 8 个 PTY 和保存线程在计时前预热；每轮各 1000 次快照构造/销毁、不变布局观察、尺寸预检和解析/编码，另有 100 次逐个完成的 fsync/rename 保存。旧 v1 字节指纹一致。保存队列在计时前清空，不能将旧完成结果当作本次提交完成。

| API | 配对中位变化 | 五组范围 |
| --- | ---: | ---: |
| 快照构造/销毁 | −11.66% | −14.26%～+2.49% |
| 不变布局观察 | −12.92% | −19.65%～−10.23% |
| 恢复尺寸预检 | −59.40% | −61.28%～−56.04% |
| 解析和编码 | −10.94% | −12.46%～−8.10% |
| 提交至保存完成 | −0.52% | −5.57%～+6.28% |

各组自身中位约为：快照 64.21→57.38 ns、观察 74.00→62.26 ns、预检 60.95→24.46 ns、格式转换 513.37→456.89 ns。它们的比值与配对中位不是同一统计量。保存包含磁盘与调度波动，不能称为稳定提速。time -lp 整测试进程高水位 RSS 配对中位 +16 KiB，范围约 −1296～+144 KiB；CPU 中位 +0.01 s、范围 −0.02～+0.03 s，包含初始化、子进程、验证与关闭，不能当作 API 的单独内存/CPU 或原生输入时延。

首版固定快照并未通过性能评估：构造中位 +103.43%、观察 +79.27%，原因包括每次添加树都备份整份快照。已保留[回退数据](m4-layout-resources-cost-before-compact-snapshot.json)，随后缩小编号、移除重复备份并只比较有效区间，以上表的重新配对结果验收；没有用零分配代替性能结论。

# 30 分钟无头长测（M8）

`ci/soak-x11.sh` 在 Xvfb 里跑**真实** congminal 进程（不是测试夹具），按固定间隔采样
RSS / 线程数 / fd / CPU，中途用 `xdotool` 打字、开关 Git 与监控面板、改窗口大小，
末尾留一段完全静默的窗口测空闲 CPU。

- 脚本：`ci/soak-x11.sh`（`sh -n` 通过，无外部依赖除 Xvfb/xdotool/ps）
- 被测版本：`target/debug/congminal`，debug 构建（未优化，内存比 release 偏高）
- 环境：Linux，Xvfb `:95`，800×480，无合成器
- 本轮：2026-10-27T18:09:27Z 起，1800 s，采样间隔 15 s，预热 20 s 后计基线
- 原始采样：`/tmp/soak2-30min.txt`（138 行，未入库；需要时重跑脚本即可复现）

## 怎么读这些数字

- **RSS 增量主要是终端回滚**：脚本持续往终端里打字并输出，滚动历史按 `DEFAULT_SCROLLBACK`
  上限 10 000 行增长，这部分内存是**有界**的（到上限后不再增长），不是泄漏。所以脚本把
  “总增量”降级为提示，只把**稳态漂移**（前 1/3 平均与后 1/3 平均之差）当失败条件；
  本轮漂移 7 746 KiB 已经接近 8 192 KiB 阈值，主要就是回滚还没填满。
- **fd 在 11 与 27 之间来回**：`sysinfo` 按 `FILE_HANDLES = 16` 的句柄缓存加上进程表刷新
  的临时句柄，采样那一刻正好在开关句柄时读数就偏低。稳定区间是 27–28，不随时间增长。
- **线程 7–8**：多出来那一条是采样/查询的命名工作线程，`LatestTask` 复用同一条线程，
  不会随采样次数增长。
- **静默 CPU 0.35%**：静默期脚本先删掉输出标记文件，让 shell 真的不再产出；这个数字包含
  监控页每秒一次的本地采样（`/proc` 读数 + 磁盘）。

## 这轮实测暴露并修掉的问题

1. **`sysinfo` 的 `/proc/<pid>/stat` 句柄缓存**：默认给每个进程留一个 fd（本机 553 个进程 →
   557 fd），且首次使用时把 `RLIMIT_NOFILE` 软上限提到硬上限。现在用
   `set_open_files_limit(16)` 压住，并把“进程列表”做成可关的配置项。
2. **静默期 CPU 偏高是脚本自身的 bug**：早期版本在“静默期”里仍让 shell 每 0.2 s 输出一次，
   读到的 3.2% 是 shell 的 CPU 而不是应用的。改成用标记文件控制输出后降到 0.35%。
3. **fd 增长的归因**：一开始以为应用泄漏 fd，单独复现打字/开关面板/改窗口都不涨，
   最后用独立探针确认增长来自 `sysinfo` 的进程表刷新（`FileCounter`）。

## 未验证

- 只跑了 debug 构建；release 的 RSS 基线会更低，但阈值是增量口径，结论不受影响。
- 只在 Linux/X11 + Xvfb 下跑过；macOS/Windows 与真实合成器、真实 WM 都没有长测。
- 没有做 GPU/图形密集场景，也没有跑真实 SSH/SFTP 会话（脚本只用本地 shell）。
- 不是 CI 作业：需要 Xvfb 与 xdotool，且 30 分钟不适合放进每次 PR 检查。

# SFTP统一文件任务的同负载成本

状态：本机成功文件路径已完成两批各五组交替对照及真实回归。保留自写有界任务适配候选，继续工作区接线；不据此启用默认发布入口或勾选完整M6。没有新增Cargo依赖、并发槽或运行时线程。

后续[工作区文件拥有者与后台认证暂存](m6-sftp-workspace-files.md)已接入测试候选；本页测量仍对应当时源码，不作为新增Workspace路径的性能结论。

## 对照与计量边界

[Service](../../src/sftp/service.rs)抽出共用的prepare_file/capture，实际提交路径与[成本夹具](../../src/sftp/service_cost.rs)使用相同DTO、路径/身份/输入额度、execute与提交/回收代码。执行器仅抽出原运行时预留公式，以便同步控制使用相同输入上限。未另写较弱的文件传输算法作为基线。

direct在测试线程同步执行；pool使用真实Service的2工作器和1回收器。两者均关联16MiB子池，遵守相同输入上限和9MiB IO余量策略，使用同一生成的加密密钥、立即回答的模拟认证前端、私有IPC/helper、OpenSSH及严格主机记录。逐项上传、下载各32MiB；两项均包含新建SSH连接、认证、源/版本检查、流式IO、原子不覆盖发布和显式回收。每项的前端线程和其模型栈预留也相同。它是成功负载的成本控制；direct缺少队列、背压、取消与UI隔离契约，不能作为可部署的等价替代。

源文件在测量前准备，字节核对在测量后执行。分别测启动API、上传完整任务、下载完整任务和关闭/join；active total为四者之和，排除前后各300ms空闲。启动API返回不保证所有线程已经运行，其余启动成本会计入后续阶段。不是连接复用或稳态网络吞吐，也没有GUI呈现/输入延迟数据。

[复现工具](../../tools/check_sftp_service_cost.py)只用Python标准库和现有采样工具，生成独立回环sshd/密钥/配置，不读取用户SSH文件。release、每种模式两次预热后五组交替；记录原始输出、阶段、每次进程树样本、源码/工具/依赖清单与产物SHA。平台macOS 27.0.1 arm64，Rust 1.99.0，OpenSSH 10.3p1/LibreSSL 3.3.6。此次测试程序6799368 B、helper 571976 B，属于测试产物/辅助程序的绝对大小，不是主程序体积增量；编译日志保留，不把缓存构建时间当作增量构建成本。

## 耗时

每组计算100×(pool/direct−1)，再取五组中位及范围，正值表示任务池较慢；不是两组中位数相除。时间包括文件同步与连接/认证等环境成本。初始批次工具尚未生成绝对差和资源汇总，原始数据完整保留；第二批扩充汇总，Rust源码相同。

| 批次/阶段 | 配对中位差 | 五组范围 |
|---|---:|---:|
| 初始上传 | −0.34% | −1.00%～+2.24% |
| 初始下载 | +0.54% | −1.48%～+4.34% |
| 初始active total | +1.25% | −0.96%～+1.87% |
| 最终上传 | +0.66% | −0.36%～+2.64% |
| 最终下载 | −0.36% | −2.01%～+3.18% |
| 最终active total | +0.53% | −0.62%～+1.37% |

最终批次active total配对绝对增量中位3.287ms，范围−3.871～+8.424ms；启动API增量中位26.292µs（23.500～70.583µs），关闭/join增量190.624µs（174.126～193.166µs）。极小同步控制的启动/析构不适合用百分比作采用结论。direct和pool各自总耗时中位625.739/624.534ms并不否定配对增量为正：中位数的排序配对不同，不混用两种统计。

两批所有测量配对的上传/下载/总耗时均未超过+5%，只表明该成功回环负载没有测得超门槛回退。预先规定的两次预热仍保留：两批首次direct上传分别671.655/1084.531ms，是明显冷样本；不能用剔除预热后的数据声称冷启动没有额外成本。[初始批次](m6-sftp-service-cost-initial.json)、[最终批次](m6-sftp-service-cost.json)。

## CPU、RSS与线程/进程

客户端树包含测试程序、OpenSSH及短时helper；另采自建服务端树，不把外部进程成本隐藏。每约5ms采样一次，实际时间戳保留；RSS是观察到的进程RSS之和，共享页可能重复，短进程/峰值可能漏采。每PID CPU用阶段内最大/最小累计计数差求和，缺少阶段边界和短命进程的完整CPU，是观察下界。短启动/回收阶段不足三样本时标为不可用。

最终批次以下为五组配对差的中位数，CPU为单核百分点，RSS为KiB；不是程序全场景上限。

|---|---:|---:|---:|---:|
| 传输前空闲 | +336 / +336 | 观察值0 | 0 / 0 | 观察值0 |
| 上传 | +240 / +256 | −0.577 | +304 / 0 | +0.781 |

客户端上传RSS中位配对范围+192～+288KiB，下载+128～+936KiB；服务端上传范围−344～+776KiB，下载−1296～+504KiB。CPU配对范围也有波动：客户端上传−1.028～+2.094、下载−1.255～+1.993个百分点；服务端上传−0.893～+2.779、下载−2.322～+1.004个百分点。不据小幅中位差宣称加速或CPU零成本。

测试根线程空闲2→5、任务期间3→6，即任务池固定多3线程；两种模式客户端观察到最多3进程，服务端最多4进程，没有逐文件新增常驻线程。两段300ms空闲各裁去50ms边缘后CPU计数没有增长，只是短采样结果，不能证明30分钟空闲增量≤0.2个百分点。每任务仍新建连接/认证，小文件与多任务启动成本须继续测量。

独立1秒忙循环检查现有libproc采样单位：Python process_time为999873000ns，观察997222458ns，比值0.997349；Mach时基125/3。[校准原始样本](m6-sftp-service-cost-cpu-calibration.json)。它证明单位换算在该进程可比，不补回漏采子进程CPU。

两模式受管峰值分别1553480/6491776 B，差4938296 B主要来自固定运行时/模型栈预留；它不同于RSS增量。共同模拟前端的1MiB栈及64KiB余量也计入受管峰值。每次显式关闭后父额度归零，双向逐字节验证、部分文件/子进程残留检查通过。受管额度不覆盖allocator/C/OS内部、实际栈承诺、页缓存等完整进程内存。

## 回归与决定

[14项构建/静态/MSRV检查](m6-sftp-service-cost-build.json)通过：默认debug/release各481项、35忽略，原生各490项、37忽略；主机默认/原生及Linux/Windows默认all-target Clippy、Rust1.88原生release编译和Service/执行器/预算实际测试、默认程序/helper生产构建。新增的是一项显式运行的忽略成本夹具，没有新增常规功能测试；交叉静态检查不是真机验收。

当前源码重新通过[15类真实文件任务](m6-sftp-service-cost-transfer.json)、[8类目录任务](m6-sftp-service-cost-service.json)、[12类工作区目录/认证/退出](m6-sftp-service-cost-workspace.json)，包括元数据压力下双方向各32MiB、取消/过期版本/错误认证/失败清理。工作区夹具仍用本地测试PTY与软件画布，不是实际SSH终端窗口组合。

当前/Rust1.88两工具链另复验文件任务和工作区全线程请求计量。文件最大字段仍在13项后因输入限额拒绝，IO实填后子用量16665128 B，请求峰值11730529/11730938 B，父预留覆盖；Status跨关闭保留，最后请求和父预留均归零。[文件当前](m6-sftp-service-cost-file-allocation.json)、[文件MSRV](m6-sftp-service-cost-file-allocation-msrv.json)。工作区/迟到输入请求峰值1316637/1317046 B，最后新增请求和SFTP父预留归零；root_total仍有其他应用资源，不宣称整个应用清空。[工作区当前](m6-sftp-service-cost-workspace-allocation.json)、[工作区MSRV](m6-sftp-service-cost-workspace-allocation-msrv.json)。临时副本的epoch计量排除计量头、allocator/C/OS、实际栈/RSS，预热已有全局线程初始化；工作器为替身，不是完整网络IO分配证明。与上一IO阶段峰值相同，共用捕获重构没有增加这两组负载的请求峰值。

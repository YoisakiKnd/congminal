# M4 搜索查询、KMP 与检查点资源准入

2026-10-25。新增 `search-reserved`，查询/预编辑 String、KMP 字符/前缀数组、最近坐标、检查点坐标与匹配队列均在分配前准入。搜索输入通过方法修改，外部只借用文本；检查点不再临时克隆队列，重扫及前后导航优先复用已有容量。无新增 Rust 包、线程或运行时子进程。**本页只覆盖 Search 拥有的动态缓冲，不是完整 M4、完整应用堆/RSS 或全部交互延迟验收。**

## 边界与所有权

- 查询和预编辑仍各最多 **1024 UTF-8 B**，不在字符中间截断。查询输入使用 1 KiB 固定栈块过滤，保留原有最多检查 1024 个字符和忽略控制字符的规则，不先创建临时 String。这个栈块有明确上限，但实际栈不属于本页堆请求计量。
- 两个文本缓冲各持有票据，扩容前覆盖旧、新容量重叠。拒绝查询扩容时保持旧查询、光标和原匹配；预编辑扩容失败时清除旧预编辑，显示资源不足状态。正常提交后清除预编辑内容，保留已计费容量以复用。
- Run 的五个缓冲先整体申请额度，再分配：`pattern`、`prefix`、`recent`、`saved`、`matches`。前四个由查询字符数限定，匹配最多 **1024** 个；最近/检查点队列按下一次幂保守预留可能的容量取整，分配后收紧到实际容量。票据放在数据字段之后，数据销毁后才归还。
- 最大查询为 1024 个 ASCII 字符时，Run 五缓冲共 **110592 B**；再加查询及预编辑各 1024 B，合计 **112640 B**。这不包括外层 Search/Run 描述符、根预算本身、分配器/C/OS 和输入事件。描述符是所属对象内的固定数据，后续完整元数据阶段继续覆盖。
- 查询变短、重新扫描、反向跨匹配窗口导航时复用已足够的五缓冲。查询变长确需更大 Run 时，新旧 Run 同时持票，原预算不变；不能把单个 Run 的数字当作重建期间整个应用峰值。
- 若文本修改成功、但新 Run 准入失败，会清除旧查询对应的匹配并停止扫描，显示“资源额度或输入长度不足，请调整后重试”；显式重开搜索/重新编辑可再尝试，不冒充“搜索完成、零匹配”。界面前缀也检查该状态。关闭搜索释放 Run，查询和预编辑已保留的容量继续收费；Search 最后销毁时全部归还。

Search 持有创建时的预算。即使调用线程进入其他 Scope，后续输入、Run 和重扫仍使用原池，不把分配转记到调用方池。复制查询到剪贴板的请求仍为独立拥有者；平台输入事件、终端预编辑和剪贴板的完整临时副本计费不由本页代替。

## 检查点与行为

扫描到可见屏幕起点时，保存标量游标/匹配状态，并把最近坐标复制到预留的 saved 队列。终端输出 revision 改变后，把 saved 坐标复制回 recent，清理受影响的屏幕匹配再扫描。两个队列互不别名，按逻辑顺序复制；不用 `clone` 创建新容量。跨软换行、宽字符/组合字符坐标、历史淘汰、重排和备用屏幕失效规则保留。

已有五项搜索行为回归继续通过，包括 120 轮交错输出/编辑/缩放/历史变化与新扫描逐项比较。新增三项常规回归覆盖查询/预编辑拒绝、Run 增长拒绝与明确重试、预算归属、重扫/反向导航地址复用和超大 Unicode 预编辑的实际 capacity。集成测试仍保留大事件 capacity 上限断言，未改用长度代替容量证明。

扫描仍是原有每步至多 32768 个 token、每 128 次检查约 2 ms 的合作式工作预算；分配额度不能证明硬时限，系统调度、单次 token 成本和原生输入到呈现继续另验。搜索关闭/失败不会把按键送入原终端的行为由原有应用/工作区输入回归覆盖。

## 实际分配与释放

[当前工具链](m4-search-resources-allocation.json)及 [Rust 1.88](m4-search-resources-allocation-msrv.json)使用临时副本全线程 epoch Rust 请求计量器，保守包含 realloc 旧、新请求重叠。终端历史和输入夹具在测量前建立，搜索独立池的初始锁/上下文也预先建立；不包含计量器附加头、分配器保留、C/OS、实际栈或整个应用的初始资源。

最大查询/KMP、1024 个匹配和 1024 B UTF-8 预编辑从冷 Search 建立：两工具链的存活请求、请求峰值、账本保留和账本峰值均为 **112640 B**，7 次分配、0 次扩容。另测 1、2、3、5、17、513、1024 字符的冷构造，实际请求和峰值均有预留覆盖；非二次幂的预留余量不会被解释成实际分配。

同一个 epoch 持续保留冷分配标记到最终释放。此后实际输出发生一次 revision 变化，测试检查点恢复；再执行 100 轮重扫、退格/插入、预编辑及扫描，改为短查询并反向跨匹配窗口导航，最后占满预算拒绝新的 Search。暖区间请求计数、存活量和峰值均不增加，拒绝零新增分配；不是清空计量器后忽略原有对象。关闭时保留 **2048 B** 文本容量，最后 Search 销毁后本 epoch 存活请求和搜索池额度均为 **0**。

[UI 复验](m4-search-resources-ui-allocation.json)在真实 PTY/app 预热后执行原来的 5000 次 UI 更新与 500 次强制完整软件绘制，仍零新增分配；像素累积指纹与上一阶段相同。输入、搜索和通知初始状态在预热内建立，不能推广为整个输入/扫描/应用每帧零分配。

[完整回归](m4-search-resources-build.json)：普通 **553** 项、预览主程序 **556** 项及 helper **18** 项通过，专用忽略分别 38/39 项；Rust 1.88 搜索相关 **8** 项通过（另 1 个手动历史基准忽略），三目标静态 Clippy、格式及默认 release 通过。Linux/Windows 交叉检查不是运行验收。

统计分类增加后，本机 Budget/Stats 为 **296/248 B**。[SFTP 文件额度](m4-search-resources-file-quota.json)仍保留原 16 MiB 子池和 9 MiB I/O 余量，最大字段输入 2 个运行/11 个等待后由额度拒绝，最终请求及父预留归零。[Workspace/SFTP 复验](m4-search-resources-workspace.json)请求峰值 **1958005 B**，最后计量请求及 SFTP 子/父额度归零；模态直接绘制仍零新增分配。不得据此宣称原生远程用户流程或整个应用已验收。

## 同负载成本

[最终对照](m4-search-resources-cost.json)将相同夹具分别注入[改动前冻结源码](baselines/m4-search-resources-before.tar.gz)及当前临时副本，使用生产 System 分配器。各版两次整次预热后五组交替，相同历史含 ASCII、中文和组合字符；每轮 1000 次退格+插入 API、100 次重启扫描、100 次从匹配窗口首项向前导航并扫描，以及 **1000** 次实际尾部输出变化后的检查点恢复/扫描。编辑计时不含后续扫描，检查点计时不含之前的 parser 输出操作；导航每次明确选中窗口首项以覆盖跨窗口重扫，而非只量索引减一。

| API 场景 | 五组配对耗时中位变化 | 配对范围 |
|---|---:|---:|
| 退格+插入（不含扫描） | -76.71% | -80.44% ～ -75.24% |
| 重启并扫描 | -0.68% | -7.23% ～ +1.45% |
| 反向跨窗口并扫描 | +1.22% | -8.05% ～ +4.97% |
| 输出变化后的检查点恢复/扫描 | -4.86% | -5.76% ～ +4.49% |

编辑 API 每次的批次折算中位约从216ns降到51ns，包含Instant开销，不能当作完整按键响应。扫描和导航总体接近，不能把小幅变化宣称成稳定提速。该夹具最后保留的缓冲从33451B变为33620B（+169B）。整进程RSS高水位配对中位+48KiB（+16～+64KiB），CPU差值中位0s（−0.01～0s）；不能从RSS差值逐字节归因于搜索缓冲。

查询选择、全部匹配坐标和 pending 状态的累积指纹一致。逐次 API 样本及 P95/P99 均保留；这里的耗时不是原生窗口、IME/剪贴板或输入到显示延迟，也不能从一次样本推导硬截止时间。CPU/RSS 由 macOS `time -lp` 记录整个测试进程，包含历史构造、parser、计时外指纹验证和析构，CPU 分辨率 0.01 秒；与 API 区间分开解释。

补容量取整模型前的七份报告保留为 `*-before-capacity-check.json`。该轮检查点只有 100 次，配对波动较大；最终扩大到 1000 次，同一负载同时用于前后版本，旧样本不代替最终结果。闭合预算/扫描语义、UI 和 SFTP 证据由[核对记录](m4-search-resources-audit.json)关联源码、清单、工具/夹具和归档，完整目标仍标记为执行中。

剩余资源工作包括 Shell/通知/链接存储、配置/侧栏/平台临时文本、根预算及同步对象、通用后台任务与回收策略；真实输入/关闭延迟、终端兼容、三平台运行和 30 分钟长测继续验收。完整 M4–M8 未勾选，既有安装包未重打包，未提交或推送。
